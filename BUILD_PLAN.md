# The Fay — Preventive Maintenance Platform · Build Plan

Internal CMMS replacing eMaint for The Fay San Jose maintenance team.
Users: ops manager, building engineer, GM, admin (you), maintenance techs.

---

## 1. What we're building

A tool that turns a written PM schedule into a living daily workflow:

- The team opens the app and sees **today's tasks**, auto-generated from recurring schedules — nothing to remember.
- Each task is a **checklist** with required **readings** (temp / pressure / gauge), **photos**, and a **status**.
- Anything flagged `Needs Repair / Parts / Vendor / Follow-up` spawns a **work order** that stays open until closed.
- Managers get a **dashboard**: done, overdue, open deficiencies.
- Everything is logged and **exportable** for compliance / audits.

**Non-goals (explicitly out of scope):** predictive maintenance, IoT/sensor integration, inventory forecasting, multi-building, tenant-facing anything, billing. This is one building, internal only.

## 2. Stack

| Layer | Choice | Notes |
|---|---|---|
| App | Next.js (App Router) + TypeScript | UI **and** API in one codebase (route handlers / server actions). No separate API server. |
| Hosting | Vercel | Next app |
| DB | Postgres on Railway | Prisma ORM |
| Cron | Railway cron worker (or Vercel Cron) | Hits an internal endpoint to materialize task instances |
| Auth | Clerk | Roles via Clerk metadata |
| Email | Resend | Overdue / assignment notifications |
| Uploads | UploadThing | Photos on tasks & work orders |
| UI | Tailwind + shadcn/ui | Modern, professional, fast to build |

**Env vars:** `DATABASE_URL`, `CLERK_SECRET_KEY`, `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`, `RESEND_API_KEY`, `UPLOADTHING_TOKEN`, `CRON_SECRET`.

## 4. Data model

```
User          clerkId, name, email, role (ADMIN|MANAGER|ENGINEER|TECH|VIEWER)
Asset         name, category, location, readingsConfig[]?
PMTemplate    title, category, frequency (DAILY|WEEKLY|MONTHLY),
              checklistItems[], requiredReadings[], assetId?, active
Task          templateId, dueDate, assigneeId?, status
              (COMPLETED|NEEDS_REPAIR|PARTS|VENDOR|FOLLOW_UP|OPEN)
              — generated by cron from PMTemplate
ChecklistTick taskId, label, done, note?
Reading       taskId, assetId?, type, value, unit, capturedAt
WorkOrder     taskId?, title, description, status (OPEN|PARTS|VENDOR|
              FOLLOW_UP|CLOSED), assigneeId?, dueDate?
Attachment    taskId? / workOrderId?, url, caption?
AuditLog      userId, entity, entityId, action, at
```

**The one non-trivial piece:** the cron job that reads active `PMTemplate`s and creates `Task` rows on the right cadence (daily every day, weekly on a chosen weekday, monthly on a chosen day-of-month), skipping duplicates. Everything else is CRUD.

## 6. Phases + Claude Code prompts

Run these one at a time. Don't start a phase until the previous one's DoD is met.

### Phase 0 — Scaffold + auth + deploy skeleton

> **Goal:** a deployed, authed skeleton. Read CLAUDE.md first, then plan in tasks/todo.md and check in before building.
>
> Scaffold a Next.js (App Router) + TypeScript app with Tailwind and shadcn/ui. Add Clerk auth with sign-in/sign-up and a protected `(app)` route group; unauthenticated users redirect to sign-in. Set up Prisma pointed at a Postgres `DATABASE_URL` (Railway). Add a role helper reading a `role` from Clerk user metadata (default `VIEWER`). Create an empty authed home at `/today` that shows the signed-in user's name and role. Configure `lint`, `typecheck`, `build` scripts.
>
> **Definition of Done:** `pnpm build` clean; I can sign in and land on `/today` seeing my name + role; Prisma connects (migrate runs with an empty schema). Deploy to Vercel with env vars. Don't build any PM features yet.

### Phase 1 — Data model + seed

> **Goal:** the schema and seed data. Plan first.
>
> Implement the Prisma schema exactly as in docs/BUILD_PLAN.md §4 (User, Asset, PMTemplate, Task, ChecklistTick, Reading, WorkOrder, Attachment, AuditLog) with the listed enums and relations. Create the migration. Write `prisma/seed.ts` that seeds: the asset list (fire pump, generator, DOAS units, AC units, elevators, pool equipment, water softener, etc.) and the PMTemplates parsed from our PM plan — daily, weekly, and monthly — each with its checklist items and any required readings (temps, pressures, gauge readings).
>
> **Definition of Done:** migration applies cleanly; `pnpm prisma db seed` populates templates + assets; a quick script or Prisma Studio shows the daily/weekly/monthly templates with their checklist items. No UI yet.

*(I'll hand you the parsed template seed from the PM doc so this phase is fill-in-the-data, not guesswork.)*

### Phase 2 — Core PM loop + cron (MVP)

> **Goal:** the usable loop for one person. Plan first.
>
> Build `/api/cron/generate` (protected by `CRON_SECRET`): reads active PMTemplates and creates Task rows due today for daily, on the configured weekday for weekly, and on the configured day-of-month for monthly — idempotent, never duplicating a task already generated for that date. `/today` lists the current user's (and unassigned) tasks due today, grouped by frequency, with status. `/tasks/[id]` shows the checklist (tick items), reading inputs (typed number + unit), photo upload via UploadThing, and a status selector. Saving persists ticks, readings, attachments, and writes an AuditLog entry. Add a Railway cron (or Vercel Cron) calling the endpoint daily.
>
> **Definition of Done:** hitting the cron endpoint generates today's tasks with no duplicates on re-run; I can open a task, complete the checklist, enter a reading, upload a photo, set status, and see it persist on reload.

### Phase 3 — Work orders + notifications

> **Goal:** deficiencies don't get lost. Plan first.
>
> When a task is set to NEEDS_REPAIR/PARTS/VENDOR/FOLLOW_UP, prompt to create a linked WorkOrder (title, description, assignee, due date). Build `/work-orders`: list + filter by status, detail view with status transitions to CLOSED, photos, and assignment. Wire Resend to email the assignee on work-order assignment and to email managers a daily digest of overdue tasks + open work orders (triggered from the cron run).
>
> **Definition of Done:** flagging a task creates a tracked work order; reassigning sends an email; a work order can be moved to CLOSED; overdue digest sends. Every mutation is server-auth-checked.

### Phase 4 — Dashboard, roles, export

> **Goal:** manager visibility + audit output. Plan first.
>
> Build `/dashboard`: today's completion rate, overdue count, open work orders by status, recent activity. Enforce roles: ADMIN/MANAGER see everything and can edit templates + assign users; ENGINEER/TECH see and complete their tasks; VIEWER read-only. Add `/admin` for managing PMTemplates and user roles. Add CSV + PDF export of completed tasks and work orders over a date range (for audits).
>
> **Definition of Done:** each role sees the correct surface and is blocked from actions they shouldn't have (verified server-side, not just hidden in UI); dashboard numbers match the data; export produces a correct file for a chosen range.

### Phase 5 — Field / mobile polish

> **Goal:** techs actually use it on a phone. Plan first.
>
> Make the task-completion flow mobile-first: large tap targets, one-thumb checklist, fast camera capture, minimal typing for readings. Make logging resilient to flaky signal in mechanical rooms (optimistic save + retry, or a lightweight offline queue for ticks/readings/photos that syncs when back online). Add a home-screen-installable PWA manifest.
>
> **Definition of Done:** I can complete a full task on a phone in a low-signal spot without losing data; the app installs to the home screen.
